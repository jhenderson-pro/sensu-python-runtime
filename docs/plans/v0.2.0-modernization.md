# v0.2.0 Modernization — Phased Task Plan

This is the work-tracking document for the v0.2.0 modernization. It is *ephemeral* working state — feel free to edit, check off, and amend as you go. The canonical project context lives in `/CLAUDE.md`; this file is just the to-do list.

Phases run in order. Do not start Phase N+1 until Phase N's exit criteria are met.

## Phase 2 — Build the core engine

**Goal:** A working local build that produces a Sensu-shaped tarball from upstream `python-build-standalone`. No CI yet.

### Tasks

- [ ] **2.1 — Pick the upstream release.**
  Visit <https://github.com/astral-sh/python-build-standalone/releases> and pick the latest release that includes Python 3.13.x with both `x86_64-unknown-linux-gnu-install_only.tar.gz` and `x86_64-unknown-linux-musl-install_only.tar.gz` artifacts. Record the release tag and SHA-256 hashes in `build/upstream.json` (a small JSON file we'll use as the pin).

- [ ] **2.2 — Write `build/fetch-upstream.sh`.**
  Reads `build/upstream.json`. Downloads the two `install_only` tarballs into `build/cache/`. Verifies their SHA-256 against the pinned values. Fails loudly on mismatch. Idempotent (skips download if cached file matches).

- [ ] **2.3 — Write `build/repackage.sh`.**
  Takes a libc target (`glibc` or `musl`) as input. Extracts the corresponding upstream tarball into a working directory. Inspects the layout (upstream uses `python/install/bin/...`). Flattens it so the resulting tarball has `bin/python`, `bin/python3`, `bin/pip`, `lib/...` at the top level — which is what Sensu agents expect when they prepend the asset to `$PATH`. Produces `dist/sensu-python-runtime_<version>_python-<py-version>_linux_amd64_<libc>.tar.gz`.

- [ ] **2.4 — Write `build/smoke-test.sh`.**
  Extracts a built tarball into a temp dir. Runs:
  - `bin/python --version` (verifies the binary executes)
  - `bin/python -c "import ssl; print(ssl.OPENSSL_VERSION)"` (verifies SSL module loads)
  - `bin/python -c "import sqlite3; print(sqlite3.sqlite_version)"` (verifies a common stdlib C extension)
  - `bin/pip --version` (verifies pip works)
  Exits non-zero on any failure.

- [ ] **2.5 — Write `build/generate-asset.sh`.**
  Generates the `core/v2` Asset YAML for a release given a version, using filenames and SHA-512s computed from the built tarballs. Output goes to `dist/asset.yml`.

- [ ] **2.6 — Local end-to-end test.**
  Run `fetch-upstream.sh`, then `repackage.sh glibc`, then `smoke-test.sh dist/<the-glibc-tarball>`. Repeat for musl (run musl smoke-test inside an Alpine container — `docker run --rm -v $(pwd):/work alpine:3.20 sh -c "cd /work && build/smoke-test.sh dist/<the-musl-tarball>"`). Both must pass before declaring Phase 2 done.

### Phase 2 exit criteria

- `make build` (or equivalent — a Makefile or `just` recipes are nice-to-have here) produces two valid tarballs locally.
- Both tarballs pass smoke tests on their respective libc.
- No `gcc`, `./configure`, or `make` for CPython itself appears anywhere. We are repackaging, not compiling.

## Phase 3 — CI/CD release automation

**Goal:** A `git tag v0.2.0-beta.1 && git push --tags` produces a complete GitHub Release with tarballs, checksums, SBOMs, provenance attestations, and a generated Asset YAML.

### Tasks

- [ ] **3.1 — `build.yml`** — PR-triggered. Runs lint (shellcheck, hadolint), `fetch-upstream.sh`, both `repackage.sh` invocations, both smoke tests. Uploads tarballs as workflow artifacts (not a release). This is what gates merges.

- [ ] **3.2 — `release.yml`** — Tag-triggered (`v*`). Runs the full build. Generates SHA-512 checksums file. Generates SBOM via `anchore/sbom-action`. Calls `actions/attest-build-provenance` for each tarball. Generates `asset.yml`. Creates a GitHub Release and attaches: both tarballs, `sha512-checksums.txt`, both `.sbom.json` files, `asset.yml`.

- [ ] **3.3 — `upstream-bump.yml`** — Scheduled daily. Polls the `python-build-standalone` releases API. If a newer release exists for our pinned Python minor, opens a PR that updates `build/upstream.json` with the new tag and hashes. Body of the PR links to the upstream release notes.

- [ ] **3.4 — `security.yml`** — Scheduled weekly. Runs trivy/grype against the latest release artifacts and posts results to the Security tab via SARIF upload.

- [ ] **3.5 — Dependabot.** `.github/dependabot.yml` with weekly updates for `github-actions`.

### Phase 3 exit criteria

- A throwaway tag (`v0.2.0-alpha.1`) on a private branch produces a complete release with all attachments.
- Provenance attestations are visible on the GitHub Release page.
- The upstream-bump workflow runs successfully (test it manually with `workflow_dispatch`).

## Phase 4 — Community beta launch

**Goal:** `v0.2.0-beta.1` is published, registered on Bonsai, and announced to the Sensu community.

### Tasks

- [ ] **4.1 — Build out `examples/simple-check/`** — a stdlib-only check (e.g., disk usage via `shutil.disk_usage`).
- [ ] **4.2 — Build out `examples/dependency-check/`** — uses `requests` (or `httpx`), vendored via `uv pip install --target lib`. Includes its own `bin/wrapper.sh` that sets `PYTHONPATH`.
- [ ] **4.3 — Build out `examples/plugin-template/`** — a documented scaffold others can copy. Include a small `Makefile` or `justfile` with `vendor`, `package`, and `clean` recipes.
- [ ] **4.4 — Write `docs/quickstart.md`** — install runtime asset, install simple-check asset, register both with Sensu, run the check.
- [ ] **4.5 — Write `docs/packaging-python-checks.md`** — the canonical guide. Covers the `bin/`/`lib/` structure, vendoring with uv, the `PYTHONPATH` wrapper, and common pitfalls.
- [ ] **4.6 — Write `docs/troubleshooting-tls.md`** — the SSL_CERT_FILE / SSL_CERT_DIR guide. Provide ready-to-copy Sensu check command examples for Debian/Ubuntu, RHEL-family, and Alpine.
- [ ] **4.7 — Write `docs/migration-from-0.1.md`** — for users coming from the original 3.6.11 asset. Note the obvious breakages: removed `imp`, removed `distutils`, syntax that didn't exist in 3.6, etc.
- [ ] **4.8 — Tag `v0.2.0-beta.1`** and let Phase 3's `release.yml` produce the release.
- [ ] **4.9 — Submit to Bonsai.** Follow the Bonsai onboarding process. The `.bonsai.yml` is now real, not a placeholder.
- [ ] **4.10 — Announce.** Write a short post for Sensu Discourse and/or the Sensu community Slack. Be explicit that this is a *beta* and ask for testing in non-production environments.

### Phase 4 exit criteria

- Asset is live on Bonsai.
- At least one external user has tested and reported back (positive or negative — both are useful).
- Issues opened during the beta are triaged within a week.

Defer everything below until the beta has been in the wild for at least two weeks with no critical issues.

- [ ] **5.1** — Add arm64 builds (mostly free; `python-build-standalone` ships them).

- [ ] **5.5** — Cut `v0.2.0` (no `-beta`).
